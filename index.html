为什么这份作品集长这样

不是「会用 AI 工具的人」，
是能把创作流程拆成 Agent 行为的人。

剪映这类产品的难点早就不在「能不能生成」，而在「生成之后能不能改、改得对不对、下一次会不会更准」。 这个岗位要的是：能定义什么叫「做得好」，能设计出让模型做得到的流程，能用测试证明它变好了。

用一句话说明我的差异

大多数 AI 创作作品展示的是「生成结果」。
我展示的是「生成过程中的判断」——
哪一步该让模型自己决定，哪一步必须停下来问人，哪一步失败之后还能退到哪。

A · Agent 机制理解

能把一个需求画成 DAG，说明每个节点的输入输出、验收条件、失败后的降级路径，以及哪些步骤必须停下来问人。

B · 效果定义

把「好」拆成 6 个可打分维度，写出 1–5 分锚点，设定通过线与否决项，让两个人独立打分能打出一致的结论。

C · 内容生产

写过脚本、拆过分镜、对过字幕、调过节奏；知道创作者在「第 4 次改开头」时最想摔电脑。

D · 数据与实验

从 50 条反馈到需求池再到实验方案，写得清样本量、护栏指标和「什么情况下承认假设错了」。

PROJECT 01  ·  AI 短视频创作 Agent

创作者不缺「生成」，
缺的是「一次改对」。

CreatorPilot 不是一个「输入提示词、输出视频」的页面。 它把一句自然语言需求编译成结构化约束 + 可执行任务图， 每一步产出都附带检查项，失败有降级路径，关键节点停下来问人—— 让 Agent 交付的不是一条视频，而是一份用户能看懂、能改、能复用的创作计划。

「我不怕它生成得丑，我怕它生成得不对，而且我不知道该改哪一句。 改到第四遍的时候，我干脆自己剪了。」 —— 创作者访谈原话（定性访谈，n=6，非定量调研）
01 / 问题

AI 已经能生成画面、配音、字幕，但「生成得对不对」没有被定义。用户只能反复重生成，把 Agent 用成了老虎机。

02 / 洞察

竞争点正从生成质量转向修改成本。一条 30 秒视频的真实成本，70% 花在「第 2 遍到第 4 遍」。

03 / 方案

计划先于生成：先出约束清单与任务图，用户确认后再执行；每步可检查、可回滚、可人工接管。

三个关键取舍 · 为什么不是另一种做法

① 计划可见 vs 一步到位
多了一次确认，换来了「改哪一步」的能力。一次性生成看着爽，但错误不可定位。

② 少打断 vs 可撤销
不做「每步都问」，而是设确认预算：一条视频最多打断 3 次，且只打断不可逆操作。

③ 通用 Agent vs 场景化
先做垂直场景，因为只有约束收敛，质量才可被定义、评测才可复现。

一个反直觉的发现

我原本以为最痛的是「生成质量不够好」。但访谈里被提到最多的不是质量，是失控感—— 用户不知道 Agent 现在在做什么、为什么这么改、失败之后会不会全丢。 P6（过程黑箱）与 P1（编辑越界）合起来占全部抱怨的 41%， 而这两个问题都属于「机制设计」，不属于「模型能力」。

因此，需求优先级不是按「技术难度」排的

而是按「用户能否自己修复」排的。凡是失败后用户还能自己动手的（P4 字幕、P8 二次调整），优先级一律下调； 凡是失败后用户只能重来的，全部进入 P0。

痛点必须变成可测量的指标 · 否则「优化」只是一句口号

定位句 · POSITIONING STATEMENT

给有剪辑基础、正在高频更新的创作者， 一个能先出计划、再做执行、边做边被检查的创作 Agent， 让她在第 2 遍修改时只需要说「改这里」， 而不是重新描述整条视频。

三条设计原则（后续每页都在用）
① 计划先于生成先让用户看到「我要做什么、按什么顺序」，再消耗生成额度
② 每一步可检查每个节点有输入、输出、验收条件；不合格不往下走
③ 失败要能降级不允许「崩掉重来」，只允许「退一步继续」

① 把工具当函数直接串起来　没有契约、没有失败码，一处失败整条链崩掉，也无法判断该重试还是该放弃。

② 让规划层直接读工具的原始返回　上下文被原始数据撑爆，节点之间产生隐式耦合，局部重跑就失效了。

③ 失败后用同一个工具原地重试　同因失败必然重复失败，还烧掉预算，最后连降级的机会都没有。

Agent 的「好不好」，
必须先被写成可打分的句子。

生成模型不是确定性的，所以「我试了一下感觉还行」不能作为结论。 评测要解决三个问题：测什么（任务集是否覆盖真实难度）、 怎么判（评分锚点是否可复现）、测出来能干什么（结论能否变成需求）。

必须先说清楚的口径

本评测的被测对象是我自建的原型，其工具调用为模拟实现。 因此本文所有分数标注为「原型态基线」，用途是验证评测流程本身可用、并暴露设计缺陷， 不代表任何真实模型的能力水平。真实模型评测需要相同的任务集与 Rubric，替换被测对象即可复用。

三层评测框架 · 不同层用不同方法
L1 能力层 · 能不能做PASS / FAIL

给定输入能否产出符合格式的产出。二值判定，不看优劣。
方法：自动检查器（结构、字段、时长、画幅）

L2 质量层 · 做得好不好1–5 分

脚本逻辑、分镜连贯、素材匹配、指令遵循程度。
方法：双人独立评分 + κ 一致性检验 + 分歧仲裁

L3 体验层 · 用得顺不顺计数 / 时长

完成所需步数、确认次数、人工干预次数、可见性。
方法：过程记录（操作日志 + 原型埋点）

五个让结果可信的设计 · 缺一个，分数就不可比
① 每任务重复 3 次

非确定性系统跑 1 次没有意义。3 次用来算一致性，第 1 次通过但第 2 次失败，本身就是结论。

② 双人独立评分

先各自打分再对答案，避免锚点被一个人带偏。加权 κ=0.71，处于「可接受」区间。

③ 分歧仲裁规则

差 ≥2 分必须回看证据并写下理由；差 1 分取均值。仲裁记录保留，是改进锚点的原料。

④ 否决项（Veto）

出现合规问题或事实错误，无论其他维度多高一律判失败。否则会出现「用高分掩盖致命错」。

什么不算评测（我刻意避免的三种做法）

① 只挑成功案例展示　这是演示，不是评测。评测的价值在于失败分布，而不是最好看的那一次。

② 用「平均分」掩盖方差　同样的均值，一个是稳定 3.5，一个是 5 和 2 交替——后者不可用于生产。

③ 只测模型，不测机制　本岗位要评的是「产品效果」，包含工具编排、降级、确认策略，不只是模型输出。

CASE 01 · T16 3 次中 2 次失败
「只改开头」，卖点被一起改了

现象　用户说「开头改得更有冲击力」，Agent 重写了整段脚本：卖点 2「续航 14 小时」被改成「一天一充」，卖点 3 直接消失。

证据　B1：改一个镜头需要 4 个手动动作；第 4 行编辑可控三家最高只有 ◐。

验证指标
重复描述次数 −50%；风格记忆关闭率 <15%

05Skill 设计说明 / SKILL DESIGN
一个可复用的短视频创作技能
写清输入、步骤、输出与校验

Skill 不是「提示词模板」，
是带校验的流程封装。

提示词模板只解决"怎么说"，Skill 要解决的是"按什么顺序做、每步怎么判合格、不合格怎么办"。 它必须能被引用、组合、评测、版本化——否则只是把 prompt 换了个地方存。

三者的区别（很容易混）
形态解决什么能否被评测
Prompt一次对话里怎么说难（无稳定输入输出）
Tool一个原子能力（生成/检索）能（有契约）
Skill一串工具 + 判断 + 兜底的组合能，且必须能
为什么 Skill 必须带 eval

技能一旦被复用，它的错误也会被批量复制。所以每个 Skill 上线前必须绑定一组 benchmark 子集：T07 / T10 / T16 全过才允许发布新版本； 版本回滚的成本必须低于修复的成本。

Skill Hub 的四条设计原则 · 决定这个生态能不能长大
① 可发现

用户说需求，系统匹配技能，而不是让用户逛"技能商店"。用意图检索，不用分类目录。

② 可组合

上一个技能的输出能直接作为下一个的输入。否则技能越多，用户越难用。

③ 可评测

每个技能绑定 benchmark 子集与通过线。没有评测的技能不允许进入推荐位。

④ 可版本化

语义化版本 + 灰度 + 一键回滚。技能是会被依赖的，改动必须向后兼容。

一个判断：Skill 的护城河不是数量，是「复用率 × 通过率」

100 个没人用的技能不如 5 个被反复用且稳定的技能。所以 Skill Hub 的核心指标不该是"技能数"， 而是复用率（同技能被 ≥3 次使用的用户占比）与通过率（用该技能完成的任务占比）。

风险：技能会僵化创作。如果所有用户都用同一个"爆款结构"，内容会趋同—— 所以技能应该封装流程，而不是封装风格。

05Memory 策略说明 / MEMORY
记什么 · 什么时候写 · 什么时候该忘

记忆的价值不是「记得多」，
是少问一次，且不问错。

记错了比不记更糟：用户要花精力去纠正，还得重新建立信任。 所以这套设计的重心在写入门槛与纠错成本，不在"能记多少"。

三层记忆 · 生命周期完全不同
层级记什么写入触发生命周期用户可见性
会话态 当前任务的约束、已确认项、未完成项 自动，随对话产生 任务结束即销毁 全程可见（就是计划面板）
项目态 这条视频的素材、版本、修改历史 自动，随项目创建 30 天无访问则归档 可查、可回溯、可删除
个体态 风格偏好、禁用词、常用结构、受众画像 需 2 次证据或显式告知 180 天衰减，可续期 设置页可查看 / 编辑 / 关闭

三层分开的意义：会话态解决"这次别忘"，个体态解决"下次别问"。混在一起就会出现"我随口说的一句话被记了半年"。

写入规则 · 四道闸门

① 显式 > 隐式　用户说「记住我喜欢克制风格」→ 直接写；从行为推断 → 需 2 次同类证据。

② 只记"稳定的偏好"　一次性的临时要求（"这次短一点"）不进个体态，留在会话态。

③ 冲突以"最近 + 显式"优先　但旧值不删除，转为历史，避免"改回来"时又从零开始。

④ 敏感信息一律不写　价格、客户名单、未公开产品信息，即使被提到也不落库。

读取 · 不是"全带上"，是"挑 3 条"
检索与注入
1. 按当前任务意图检索候选记忆
2. 用「相关度 × 最近使用 × 置信度」排序
3. 只注入 Top 3，其余按需展开
4. 注入时标注来源：「根据你过去 3 次的选择」

为什么要限量：记忆越多，越容易和当前指令冲突，模型也越容易"抓着旧偏好不放"。

一个具体例子 · 记忆怎么被用起来

用户第 4 次做数码视频，输入一句话。系统检测到个体态里有 「偏好克制」「句长 ≤18 字」「常用结构：钩子→参数→对比→结论」，自动预填为约束默认值， 并在输入框下方显示：「已按你的习惯预填 3 项 · 修改」。 用户可以直接生成，也可以改——默认值是可以被推翻的，这是信任的前提。

失败模式 · 记忆会怎么坏
记忆污染把一次性要求记成长期偏好 → 用"2 次证据"门槛挡住
过度个性化永远只给同一类结果，创作失去探索 → 保留 10% 随机变体
纠错成本高用户不知道怎么删 → 设置页 + 结果页都能一键"别再这样"
隐私越界跨账号复用偏好 → 记忆严格绑定账号，不做跨端合并
为什么我把 Memory 排在 V1.0 而不是更早

因为记忆依赖两个前提：可靠的编辑记录（知道用户改了什么）与稳定的约束体系（知道该记哪几个维度）。 这两件事在 V0.5 之前都不成立——那时候记下来的都是噪声。

衡量记忆是否"有用"的唯一标准

不是"记住了多少条"，而是用户的描述字数有没有变少、关闭率有没有上升。 这两个数一个降一个不涨，才说明记忆在做正功。

关于创作者 Agent，
我现在的五条判断。

它们都不"正确"，只是我做完这一轮研究与设计后愿意为之负责的立场。 如果你不同意其中任何一条，我很想听理由。

01
Agent 的护城河不在生成，在「改」的成本。

生成能力会被拉平，修改成本不会——它取决于架构里有没有"可寻址的中间产物"。这是产品决策，不是模型决策。

02
可控性是可以被设计出来的，不是靠模型变聪明。

计划可见 + 作用域明确 + 可回滚，这三件事今天就能做。做了之后，同一个模型的表现会立刻不一样。

03
确认不是越少越好，是「确认预算」要花在用户在意的地方。

一条视频最多打断 3 次，且只打断不可逆操作。第 4 次打断之后，确认就变成了盲点。

04
Skill 的竞争不是数量，是「谁的技能可被验证」。

评测即分发。没有 benchmark 的技能不该被推荐给用户——因为它的错误会被批量复制。

05
Memory 应该是「可见的、可删的、有证据的」。

记错了比不记更伤。个性化真正的指标不是记住多少条，而是用户少说了几句话、且没有被打扰。

这五条如果被数据推翻，我会改。但在被推翻之前，我愿意按它们做决策。
